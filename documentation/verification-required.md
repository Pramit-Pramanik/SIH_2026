## 1. COMPREHENSIVE CONTRADICTION MATRIX

Every contradiction identified across the project's documentation, specifications, and architecture is cataloged below with authority levels, identified problems, prototype decisions, and production paths:

| ID | Topic | Source A | Source B | Authority Level | Problem | Prototype Decision | Production Decision | Status |
|---|---|---|---|---|---|---|---|---|
| **CTR-001** | **PostgreSQL Schema** | `hackathon-mvp-blueprint.md` early draft defined 4 tables. | `MandiQ Architecture Blueprint.md` and codebase define 8 canonical models. | Level 2 vs Level 2 | Discrepancy in table scope and column names across early blueprints. | **Adopt authoritative 8-table relational model** managed by Alembic (`mandis`, `crops`, `farmers`, `users`, `procurement_slots`, `procurement_logs`, `weighbridge_events`, `wal_mutation_journal`) with canonical naming (`land_area_hectares`, `production_ceiling_qt`). Active queue is held in Redis ZSET. Supports SQLite fallback. | Range-partitioned PostgreSQL tables on `scheduled_date` with hash sharding across `mandi_id`. | **RESOLVED IN REPO** |
| **CTR-002** | **Redis Locking Terminology** | `Mandi Queue Algorithms.md` & `dynamic-slot-booking.md` label single-node locking as "Redis Redlock Distributed Memory Locking Algorithm". | Redis Official Specification. | Level 2 vs Level 1 (Redis Spec) | True Redlock requires $\ge 5$ independent master nodes. A single Redis instance executing `SET key token NX PX 1500` with Lua release is an atomic distributed-style lock, not full Redlock. | Rename to **"Redis atomic slot lock"** or "Redis-based distributed-style lock". Prohibit over-engineering hackathon prototype with multi-node clusters. | Multi-node Redlock cluster across 5 Redis nodes or Redis Sentinel/Raft if multi-region consensus is required. | **RESOLVED FOR PROTOTYPE** |
| **CTR-003** | **Message Broker (Kafka vs RabbitMQ vs Celery vs Redis)** | `sih-presentation-content.md` lists "RabbitMQ for event-driven microservices". | `MandiQ Architecture Blueprint.md` and `backend-agent.md` list "Apache Kafka (`confluent-kafka`)" and "Celery + RabbitMQ / Redis". | Level 3 vs Level 2 | Competing messaging infrastructure mentioned. Kafka and RabbitMQ introduce heavy container and operational footprints incompatible with a 36-hour local hackathon prototype. | **Freeze to Redis in-memory pub/sub and FastAPI `BackgroundTasks`**. Strictly zero Kafka, RabbitMQ, or Celery daemons in prototype. | Apache Kafka message mesh (`mandi.events` topic) for inter-agency event streaming. | **RESOLVED FOR PROTOTYPE** |
| **CTR-004** | **Queue Implementation (SQL Table vs Redis ZSET)** | `hackathon-mvp-blueprint.md` defines an SQL table `active_mandi_queue`. | `Mandi Queue Algorithms.md` defines the active queue as a Redis Sorted Set (`ZSET`) with key `mandi:queue:{mandi_id}`. | Level 2 vs Level 2 | Maintaining queue order in both SQL and Redis causes state drift, race conditions, and dual-source-of-truth errors. | **Redis Sorted Set (`ZSET`) is authoritative for real-time queue ordering** ($O(\log N)$ priority re-ranking). PostgreSQL `procurement_logs` records state history and audit events. | Redis ZSET for live yard state + Kafka append-only log for full historical replay. | **RESOLVED FOR PROTOTYPE** |
| **CTR-005** | **DCDQ Formula & Terminology** | `Mandi Queue Algorithms.md` names $W_i$ "Anti-Starvation Wait Penalty (Max 20 points)". | Mathematical formulation: $S_i = \alpha A_i + \beta D_i + \gamma M_i + \lambda W_i$, where $W_i = \min(20.0, 0.1 \times t_{\text{wait}})$. | Level 2 | Calling $W_i$ a "Penalty" is a semantic contradiction because $W_i \ge 0$ and is positively added to $S_i$, boosting priority as waiting time increases. | Rename to **"Anti-Starvation Waiting-Time Bonus ($W_i$)"**. The mathematical formula is preserved verbatim: $S_i = \alpha A_i + \beta D_i + \gamma M_i + \lambda W_i$. Higher $S_i$ = higher queue priority (retrieved via `ZREVRANGE`). | Same formula with regional dynamic calibration for $\alpha, \beta, \gamma, \lambda$. | **RESOLVED FOR PROTOTYPE** |
| **CTR-006** | **Quality Rules vs Queue Priority** | `hackathon-mvp-blueprint.md` states high moisture exponentially scales priority ($M_i$) to prevent open-air rot. | `domain-integrity-rules.md` and `The MandiQ Platform.md` state crop lots with moisture $>17.0\%$ must trigger `QUALITY_REJECTED`. | Level 2 vs Level 2 | If a crop has $18\%$ moisture, DCDQ would compute a high moisture priority score, but quality standards mandate outright rejection. | **Strict separation of concerns**: DCDQ determines queue ordering for eligible lots. Quality rules determine procurement eligibility. Moisture $>17.0\%$ immediately triggers `QUALITY_REJECTED` and routes to drying apron, overriding queue priority unless a supervisor override is authenticated. | Same rule with automated moisture meter calibration and digital supervisor override audit logs. | **RESOLVED FOR PROTOTYPE** |
| **CTR-007** | **Yield Ceiling Authoritative Value & Concurrency** | `hackathon-mvp-blueprint.md` calls it `estimated_yield_qt` on the farmer table. | `database-schema-reference.md` calls it `production_ceiling_qt`. Invariant states $Q_{\text{sold}} \le A_{\text{hec}} \times Y_{\text{crop}}$. | Level 2 vs Level 2 | Ambiguity over whether `production_ceiling_qt` is authoritative or if every transaction must dynamically calculate $A_{\text{hec}} \times Y_{\text{crop}}$. | **`production_ceiling_qt` stored on the `farmers` record is authoritative**. Validation and reservation must occur atomically inside the same transaction/locking boundary to prevent concurrency race conditions. | Dynamic sync with state land registries (AgriStack / MFMB / e-Uparjan). | **RESOLVED FOR PROTOTYPE** |
| **CTR-008** | **DBT Authorization Cryptography** | Earlier code snippet in `antigravity-workspace-bundle.md` used plain SHA-256 (`hashlib.sha256`) with a hardcoded salt string. | Global Architecture Rules mandate HMAC-SHA256 and zero hardcoded secrets. | Level 2 vs Level 2 (Security conflict) | Plain SHA-256 is vulnerable to length-extension attacks without HMAC, and hardcoded secrets violate fail-closed security. | **Strictly enforce HMAC-SHA256 with key injected from environment** (`MANDIQ_PAYOUT_SECRET_KEY`). Fail closed if secret is missing. | Hardware Security Module (HSM) multi-signature authorization. | **RESOLVED FOR PROTOTYPE** |
| **CTR-009** | **Secret Management & Hardcoded Keys** | Code snippets in `antigravity-workspace-bundle.md` included default strings `b"MANDIQ_SECRET_HMAC_KEY_2026"` and `"MANDIQ_MULTISIG_SALT"`. | Production security rules mandate environment-injected secrets and fail-closed behavior. | Level 2 | Hardcoded secrets in code snippets lead to insecure prototype deployments. | **Remove all hardcoded secrets from executable code**. Require `MANDIQ_SECRET_HMAC_KEY` and `MANDIQ_PAYOUT_SECRET_KEY` via environment. Missing secret -> FAIL CLOSED (raise configuration error). | Vault / KMS secret manager. | **RESOLVED FOR PROTOTYPE** |
| **CTR-010** | **Offline Sync & LWW Conflict Resolution** | `hackathon-mvp-blueprint.md` proposes Last-Write-Wins (LWW) based on timestamps. | `MandiQ Architecture Blueprint.md` (GAP-002) notes rural network blackouts cause client clock drift, corrupting pure physical timestamp LWW. | Level 2 vs Level 2 | Pure physical timestamp LWW is vulnerable to client clock skew during multi-hour blackouts. | For prototype, client submits `client_mutation_id` (mutation identity / deduplication) and `client_timestamp` (diagnostic metadata only). Server assigns monotonic `server_receive_sequence` as the authoritative conflict ordering clock (later server-received mutation wins; deterministic `client_mutation_id` tie-breaker). Vector clocks and NTP are marked production-only. | APMC yard local NTP server + Vector Clocks for multi-client field synchronization. | **RESOLVED FOR PROTOTYPE** |
| **CTR-011** | **State Machine Lifecycle** | `hackathon-mvp-blueprint.md` lists 4 coarse statuses: `SCHEDULED`, `ARRIVED`, `PROCESSING`, `COMPLETED`. | `domain-integrity-rules.md` and `The MandiQ Platform.md` list 10 granular states: `SLOT_BOOKED`, `GATE_ENTRY_VERIFIED`, `IN_QA_QUEUE`, `QUALITY_APPROVED`, `ROUTED_TO_WEIGHBRIDGE`, `WEIGHED_GROSS`, `WEIGHED_TARE`, `BILL_GENERATED`, `DBT_PAYMENT_INITIATED`, `PAYMENT_SETTLED`. | Level 2 vs Level 2 | Coarse 4-state lifecycle fails to capture the gate check-in, QA moisture assaying, gross/tare scale weighments, and dual-sig payment steps. | **Adopt the canonical 10-state granular state machine** (plus `QUALITY_REJECTED` and `PAYMENT_FAILED`) across all models. | Same 10-state machine streamed via Kafka event topics. | **RESOLVED FOR PROTOTYPE** |
| **CTR-012** | **Hardware Telemetry Integration** | `Mandi Queue Algorithms.md` details ESP32, HX711 load cells, Web Serial, and Web Bluetooth. | Prototype execution requires running in standard web browsers and automated test harnesses without physical lab hardware. | Level 2 | Attempting physical hardware integration during a 36-hour prototype blocks testing and causes deployment failure. | **Implement a software weighbridge telemetry emulator** streaming synthetic weight readings via WebSocket/REST. Freeze physical ESP32/HX711/BLE drivers to P2. | Certified physical RS232 / Web Bluetooth load cell drivers. | **RESOLVED FOR PROTOTYPE** |
| **CTR-013** | **API Namespace & Routing** | `hackathon-mvp-blueprint.md` lists mock routes `/api/v1/mock/ekyc` and `/api/v1/mock/dbt-payout`. | `MandiQ Architecture Blueprint.md` references general REST endpoints. | Level 2 | Ambiguity over route prefixes. | Standardize all prototype routes under `/api/v1/` prefix with `/api/v1/mock/` specifically reserved for simulated external government services. | API Gateway with mTLS and OAuth2. | **RESOLVED FOR PROTOTYPE** |
| **CTR-014** | **Procurement Log Partitioning & SQLite Fallback** | `database-schema-reference.md` has `PARTITION BY RANGE (scheduled_date)` on `procurement_slots` but NOT on `procurement_logs` (even though Database Agent Rule 2 claimed both were partitioned). | SQLite development fallback does not support declarative table partitioning or `SERIAL` syntax. | Level 2 vs Level 2 | Direct contradiction between database agent rules and actual DDL, and incompatibility with SQLite development fallback. | **Label range partitioning as a PRODUCTION OPTIMIZATION**. PostgreSQL 16 is the production target; SQLite 3 is a development/test fallback. Application models remain portable via SQLAlchemy 2.x, but SQLite is not required to accept identical PostgreSQL DDL syntax. Prototype DDL uses standard unpartitioned tables with compound indexes. | Declarative PostgreSQL range partitioning on high-volume production databases. | **RESOLVED FOR PROTOTYPE** |
| **CTR-015** | **System Availability Language ("100% Uptime")** | `MandiQ Architecture Blueprint.md` claimed "guarantees 100% operational uptime at procurement yards". | System resilience engineering reality: Local edge computing mitigates network outages, but device power, OS crashes, or hardware damage can still halt a terminal. | Level 2 vs Level 1 (Engineering principles) | "100% operational uptime" is an absolute marketing claim that is technically indefensible. | Replace with defensible engineering contract: **"Core local operations must continue during temporary network unavailability, subject to local device availability and local storage availability."** | Same defensible SLA with local hardware redundancy. | **RESOLVED** |
| **CTR-016** | **Zero-Placeholder Rule vs Valid Ellipses** | Earlier rule claimed: "No code file, schema script, or documentation generated within MandiQ shall contain // TODO, ..., or placeholder functions." | Modern Python type annotations (`Tuple[int, ...]`, `Callable[..., Any]`) and documentation examples legitimately use `...`. | Level 5 | Globally banning `...` causes valid Python code and markdown snippets to fail static checks. | Refine rule: **"No unresolved implementation logic may remain in production code (prohibits `TODO`, `FIXME`, `NotImplementedError`, stub functions, fake success responses)."** | Same refined rule enforced in CI linters. | **RESOLVED** |
| **CTR-017** | **P0 / P1 / P2 Scope Governance** | `The MandiQ Platform.md` and `procurement-center-inefficiencies-report.md` discuss railway rake logistics, silo IoT, national customs. | `hackathon-mvp-blueprint.md` delimits scope strictly to 36-hour local hackathon prototype. | Level 3 vs Level 2 | Risk of future coding agent attempting national railway optimization or physical GSM telecom integration. | **Explicit freeze: P0/P1 only**. All railway, silo, national buffer stock, and physical telecom are strictly P2 and forbidden. | Phase 2 enterprise roadmapped features. | **RESOLVED** |
| **CTR-018** | **System Architecture (Microservices vs Modular Monolith)** | `MandiQ Architecture Blueprint.md` references "Hybrid Event-Driven Microservices Architecture". | 36-hour prototype constraint and single-container operational reality. | Level 2 vs Level 2 | Independently deployed microservices create container bloat and network configuration failure during hackathon evaluation. | **The 36-hour prototype is a modular monolith, not a collection of independently deployed microservices.** FastAPI routers are cleanly separated internally (`auth`, `farmers`, `slots`, `queue`, `quality`, `weighbridge`, `billing`, `payout`, `sync`, `mock`) within a single process. | True multi-service microservices architecture deployed on Kubernetes with Kafka event mesh. | **RESOLVED FOR PROTOTYPE** |
| **CTR-019** | **Repository Portability & Path Independence** | Early prompts contained machine-specific paths referencing developer drive letters (`file:///e:/SIH/SIH_PROJECT/...`). | Portability requirements for open evaluation and clone-safety across arbitrary developer environments. | Level 4 vs Level 1 | Absolute filesystem paths fail when cloned onto another machine or CI/CD container. | **The repository must be clone-portable. No agent, script, test, configuration, documentation link, Docker configuration, or application code may assume the original author's absolute filesystem path.** Define `PROJECT_ROOT`. All paths resolve relatively. | Same portable configuration via Docker environment variables. | **RESOLVED** |
