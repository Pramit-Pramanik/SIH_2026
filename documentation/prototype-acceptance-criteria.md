### AC-001: Mock Aadhaar e-KYC & Land Record Lookup
- **Requirement**: Retrieve verified land records and compute the maximum allowable production ceiling for an entered Aadhaar hash.
- **Given**: A registered farmer with verified land area $A_{\text{hec}} = 2.50$ hectares and registered crop yield $Y_{\text{crop}} = 25.0$ quintals/hectare.
- **When**: The client calls `GET /api/v1/mock/ekyc?aadhaar_hash=a5e87bcf921f0090de391`.
- **Then**: The system returns HTTP 200 with farmer identity details, linked land records, and a computed production ceiling `estimated_yield_quintals == 62.50`.
- **Verification**: Automated test asserting HTTP 200, schema match, and `estimated_yield_quintals == 62.50`.

### AC-002: Dynamic Slot Reservation & Concurrency Guardrail (Redis Atomic Lock)
- **Requirement**: Allow reservation of an hourly arrival slot up to allocated capacity and reject overbooking using an atomic Redis slot lock.
- **Given**: An operational mandi slot with 50.0 quintals of available remaining capacity.
- **When**: Two concurrent requests attempt to reserve 30.0 quintals each for the same slot.
- **Then**: Exactly one request succeeds with status `SUCCESS` and increments booked capacity, while the competing request is either serialized or rejected with `Slot capacity exhausted`.
- **Verification**: Concurrency stress test executing simultaneous async requests against the booking endpoint with assertion that total booked capacity never exceeds allocated capacity.

### AC-003: Offline-Validatable Cryptographic Token Generation (HMAC-SHA256)
- **Requirement**: Each confirmed slot booking must issue a tamper-proof cryptographic token signed with HMAC-SHA256 that can be verified offline without cloud connectivity.
- **Given**: A valid reservation for `farmer_id=101`, `mandi_id=1`, `slot_id=5`, and `quantity=25.0`.
- **When**: The booking token is generated by the server with `MANDIQ_SECRET_HMAC_KEY` injected from environment.
- **Then**: The token payload contains a 64-character hex HMAC-SHA256 signature calculated over `${farmer_id}:${mandi_id}:${slot_id}:${requested_qty_qt}`.
- **Verification**: Cryptographic test asserting offline signature validity using the same secret key, and rejecting when a single character in the payload is altered.

### AC-004: Fail-Closed Behavior on Missing Cryptographic Secrets
- **Requirement**: The system must fail closed and refuse to sign or verify tokens/payouts if required environment secrets are absent or empty.
- **Given**: The backend service or script executes with `MANDIQ_SECRET_HMAC_KEY` or `MANDIQ_PAYOUT_SECRET_KEY` unset or empty.
- **When**: A slot booking or payout verification endpoint is invoked.
- **Then**: The system immediately raises a fatal configuration exception (`RuntimeError` / HTTP 500), refusing to use any fallback default key or generate unauthenticated tokens.
- **Verification**: Unit test clearing environment variables and asserting that invocation raises a configuration error and blocks transaction execution.

### AC-005: Yield Ceiling Invariant Enforcement & Atomic Boundary
- **Requirement**: Under no circumstances shall a booking or transaction commit if the cumulative requested quantity exceeds the farmer's registered production ceiling ($\sum Q_{\text{delivered}} > \text{production\_ceiling\_qt}$). Validation and reservation must occur atomically inside the same transaction/locking boundary.
- **Given**: A farmer with `production_ceiling_qt = 50.0` quintals who has already booked 40.0 quintals.
- **When**:
  - Test Case A (Below ceiling): Request 5.0 quintals $\rightarrow$ Expected: ACCEPT (total 45.0).
  - Test Case B (Exactly at ceiling): Request 10.0 quintals $\rightarrow$ Expected: ACCEPT (total 50.0).
  - Test Case C (Above ceiling): Request 15.0 quintals $\rightarrow$ Expected: REJECT with HTTP 422 / domain error.
  - Test Case D (Repeated transactions): Three sequential requests of 20.0 quintals $\rightarrow$ Expected: Requests 1 & 2 ACCEPT, Request 3 REJECT.
  - Test Case E (Concurrent transactions): Two parallel requests of 30.0 quintals submitted simultaneously $\rightarrow$ Expected: Exactly one commits, the other fails ceiling check; cumulative never exceeds 50.0 quintals.
- **Verification**: Automated test suite executing Test Cases A through E against booking and weighment commit endpoints.

### AC-006: DCDQ Multi-Criteria Priority Re-Ranking & Ordering Proof
- **Requirement**: The DCDQ engine must dynamically re-rank active mandi yard vehicles based on $S_i = \alpha A_i + \beta D_i + \gamma M_i + \lambda W_i$, ensuring higher scores yield higher queue priority.
- **Given**: 
  - Vehicle A: Moisture 13.5% ($M_A = 0.0$), arrived 45 mins ago ($W_A = 4.5$), $A_A = 35.0$, $D_A = 5.0 \implies S_A = 44.5$.
  - Vehicle B: Moisture 16.2% ($M_B = 11.62$), arrived 10 mins ago ($W_B = 1.0$), $A_B = 35.0$, $D_B = 5.0 \implies S_B = 52.62$.
- **When**: The DCDQ priority scoring function executes and tokens are indexed into the Redis Sorted Set (`mandi:queue:{mandi_id}`).
- **Then**: Vehicle B achieves a higher composite priority score ($S_B > S_A$) and is retrieved first via `ZREVRANGE` / `ZREVRANGEBYSCORE` (highest score first).
- **Verification**: Algorithmic regression test verifying that higher DCDQ score strictly maps to earlier queue position in Redis ZSET retrieval.

### AC-007: Quality Rejection Overrides Queue Priority
- **Requirement**: A lot with moisture $>17.0\%$ is disqualified from procurement and must NOT be routed to the weighbridge regardless of its computed DCDQ score. High DCDQ scores must never bypass quality rejection.
- **Given**: Vehicle C arrives with moisture 18.5%.
- **When**: Moisture assay reading is entered into the system.
- **Then**:
  - The transaction state transitions immediately to `QUALITY_REJECTED`.
  - The vehicle is removed from the active weighbridge dispatch queue.
  - An advisory notice routes the vehicle to the mandi drying apron.
  - A supervisor override token can transition the lot back to active queue only with explicit audit logging.
- **Verification**: Automated test asserting state `QUALITY_REJECTED`, exclusion from active weighbridge dispatch list, and audit record generation.

### AC-008: Offline Write-Ahead Logging (WAL) & Gzip Batch Sync
- **Requirement**: Client devices must log transactions to IndexedDB `transactionsWAL` during network blackouts, compress logs with Gzip, and synchronize asynchronously upon reconnection.
- **Given**: Mandi client operating with `navigator.onLine === false`.
- **When**: Gate check-in and gross weighment transactions are recorded on the client.
- **Then**:
  - Records commit locally to IndexedDB `transactionsWAL` table with status `PENDING` and a local `client_mutation_id`.
  - Upon network recovery, sync worker compresses the payload using Gzip (<100 KB per 50 records) and posts to `/api/v1/sync/wal`.
  - Server assigns monotonic `server_receive_sequence` as authoritative conflict ordering and applies field-level LWW merge (`client_timestamp` is preserved purely as diagnostic metadata).
  - Client updates status to `SYNCED`.
- **Verification**: End-to-end integration test simulating disconnected writes, payload compression size assertion, and successful cloud ledger reconciliation.

### AC-009: Dual-Signature DBT Payout Staging (HMAC-SHA256)
- **Requirement**: Direct Benefit Transfer payout staging requires independent cryptographic authorization from both the Procurement Inspector and Mandi Operator bound to the same transaction and amount.
- **Given**: A completed weighment with generated digital J-Form invoice amount of ₹142,187.50 for transaction `TXN-2026-001`.
- **When**:
  - Test Case A (Valid dual signatures): `POST /api/v1/payout/stage` with valid `inspector_sig_hash` and `operator_sig_hash` computed with `MANDIQ_PAYOUT_SECRET_KEY` $\rightarrow$ Expected: Status `AUTHORIZED`, unique `payout_block_hash` generated, mock DBT endpoint triggered.
  - Test Case B (Single signature): Request submitted with only `inspector_sig_hash` $\rightarrow$ Expected: HTTP 403 / REJECTED (`Missing Operator Signature`).
  - Test Case C (Wrong signature): `operator_sig_hash` is forged or mismatched $\rightarrow$ Expected: HTTP 403 / REJECTED (`Invalid Operator Signature`).
  - Test Case D (Modified amount): `invoice_amount_inr` tampered in request $\rightarrow$ Expected: HTTP 403 / REJECTED (Hash mismatch).
  - Test Case E (Modified transaction ID): Signatures from `TXN-001` reused for `TXN-002` $\rightarrow$ Expected: HTTP 403 / REJECTED (Signature cannot be reused across transactions).
- **Verification**: Automated security test suite asserting Test Cases A through E.

### AC-010: Software Weighbridge Telemetry Ingestion (WebSocket / Emulator)
- **Requirement**: Weighbridge operator interface must ingest scale readings from a software telemetry emulator rather than physical hardware.
- **Given**: Software load cell emulator streaming gross weight updates (e.g. 150.0 quintals) over WebSocket or REST.
- **When**: Operator activates "Capture Weight" in the Mandi Monitor UI.
- **Then**: The reading is stabilized, locked into the transaction record as `gross_weight_qt`, and manual keyboard editing of the scale field is disabled unless an authenticated supervisor override key is provided.
- **Verification**: Test script verifying automated telemetry stream capture and tamper-prevention locking.

### AC-011: Zero Unresolved Implementation Placeholders
- **Requirement**: No production source code file may contain unresolved implementation placeholders.
- **Given**: All source files in `backend/`, `frontend/`, `scripts/`.
- **When**: Static code audit executes during verification mode.
- **Then**: Zero instances of `TODO`, `FIXME`, `NotImplementedError`, stub functions, or fake success responses are detected.
- **Verification**: Automated ripgrep regex audit checking for banned placeholder tokens in application directories.

### AC-012: Frozen Prototype Dependency Isolation
- **Requirement**: The application runtime must execute without requiring Kafka, RabbitMQ, Celery, or physical hardware.
- **Given**: A clean execution environment with Python 3.12, Node.js 18+, and Redis 7.2.
- **When**: The full test suite and demo services launch.
- **Then**: All features (booking, DCDQ ranking, offline sync, weighment, DBT staging) execute to completion with 100% passing tests without any unfulfilled connection errors to external message brokers or cloud APIs.
- **Verification**: Automated test runner executing the complete prototype test suite in an isolated environment containing only the approved dependency baseline.
